# Codex 段落衔接复核

此阶段是 Codex 在当前任务中的语义检查，不要求用户额外提供 LLM API key，也不启动另一场 Codex 任务。脚本提供完整原文和定位材料；标点、正则或模型原有 merge 标记都不能单独决定修复。

## 读取与核对

1. 读取 `manifest.json`，记录源 SHA-256、总页数、块数和分块列表。按顺序读每个 chunk 的**主检查范围**，两端上下文用于跨块连续判断。超长单行（如大型表格）仍需按字符分段读全，不能直接跳过。
2. 需要定位时查询 `blocks.jsonl`，其行号属于原始 Markdown，页码是从 1 开始的 PDF 物理页码。一个块可能关联多个页面。PDF 上印刷的页码如不同，应另外说明。
3. 找出疑点：段尾的半个词或半句话、下一栏/页接续、图表插在句子中间、页眉页脚混入正文、无关列表条目被并在一起、段落顺序颠倒。完整自然段之间语义转换不是自动合并的理由。
4. 对疑点查看 `校对.html` 对应原文区域，或渲染 `_origin.pdf` 的相关页面。核查两侧标题、栏顺序、图片/表格位置和相邻内容。读取后续几段确认不是新章节或独立列表项。
5. 只在证据足够时提出精确修复。中文词内断开通常连接为空串；英文词间通常保留空格；行末连字符可能是断词也可能属于术语，须看原图判断。不能凭语言流畅度补写原文没有的内容。
6. 写 `修复建议.md`，去重跨 chunk 的重复疑点。报告生成后核对引文、行号、块 ID 与文件哈希；已查完全部范围才将 manifest 的 `review_status` 改为 `completed_by_codex`，并增加 `reviewed_chunks` 列表。

如果存在浮动图表，用块 ID 指明被跨过的块及其保留位置，避免建议导致图片重复或丢失。无法唯一映射、图像不清楚或缺失上下文时列为“待人工确认”。

## 报告内容

标题用“修复建议”，至少包含以下信息（可按文档规模调整排版）：

```markdown
# 修复建议

- 检查对象：原始 Markdown 文件名
- 源文件 SHA-256：实际值
- 检查范围：PDF 物理页范围、原 Markdown 行范围、已读分块数/总分块数
- 方法：Codex 全文上下文检查；对疑点核对原始 PDF 的具体页数
- 结论：确认问题数、待人工确认数；未覆盖范围（若有）

## 1. 简明描述实际断点

- 定位：Markdown 第 x、y 行；块 ID；PDF 第 n 页左/右栏或第 n、n+1 页
- 原文前段：逐字引用必要的段尾
- 原文后段：逐字引用必要的段首
- 问题与依据：为什么属于误断、误合并或顺序错误；原图证据
- 建议：具体合并/分开/移动操作，所需空格、连字符或换行
- 建议后文本：仅覆盖该断点的可核对片段
- 置信度：高/中/低及原因
- 状态：仅建议，未修改原始 Markdown
```

不要把示例占位符留在最终文件。未发现明确问题时也生成报告，写明“在上述检查范围内未发现需要修复的段落衔接问题”，并如实说明原图检查范围。不得把段落衔接检查描述成 OCR 逐字校准或准确率保证。

默认不应用修复。用户随后要求应用时，再核对源哈希，在副本中改动并给出差异；校对页原始映射和修复后映射的对应关系也要保持可追溯。
